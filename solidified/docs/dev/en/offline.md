# Offline Support

Reading works without a connection. Three layers cooperate, each covering what the one below it can't:

| Layer | File | Storage | Covers |
|---|---|---|---|
| Service worker | `build-sw.mjs` | Cache Storage | App shell, static assets, HTTP responses |
| Fetch fallback | `packages/spa-core/src/lib/offline-fallback.ts` | IndexedDB (`keyval-store`) | Every `/spa/` GET in the app |
| Message store | `packages/spa-core/src/lib/message-store.ts` | IndexedDB (`hz-inbox-*`) | Message lists and post bodies |

The layers are deliberately redundant. A service worker can fail to install, be evicted under storage pressure, or simply not be registered yet — and when that happens the HTTP-level cache disappears with it. The two IndexedDB layers belong to the app, never expire, and keep working regardless.

## 1. Service worker

Generated by `build-sw.mjs` via workbox `generateSW`, served from `/spa/sw` (`Handlers/Sw.php` sets `Service-Worker-Allowed: /` so it can claim the whole origin).

**Precache** is the app shell only — root-level hashed `app-*.js`/`.css` plus the PWA icons, about 4.7 MB:

```js
globPatterns: ['*.{js,css}', '*.{png,svg,ico}'],   // NOT recursive
maximumFileSizeToCacheInBytes: 4 * 1024 * 1024,
```

The pattern is non-recursive on purpose. `assets/` subdirectories hold 31 MB of ffmpeg wasm, 15 MB of background patterns, 10 MB of puzzle wasm and 4 MB of fonts; precaching those made SW install a 36 MB download, which mobile browsers fail or evict — and **a failed install means no service worker at all**, so every offline feature dies at once. A build-time `assert` fails the build if the precache exceeds 10 MB. If it trips, runtime-cache the new asset rather than raising the limit.

**Runtime caches**, in route order:

| Pattern | Handler | Retention |
|---|---|---|
| `/pconfig` | NetworkFirst | 1 day |
| `?format=json` | NetworkFirst | 5 min |
| `/spa/…?dbegin=` | **NetworkOnly** | never cached |
| `/spa/` | NetworkFirst | 30 days, 300 entries |
| navigations | NetworkFirst | 30 days, 20 entries |
| `/photo/` | StaleWhileRevalidate | 30 days, 500 entries |
| `assets/{fonts,patterns,bg,puzzles}/` | CacheFirst | 30 days, 80 entries |
| remote images | CacheFirst | 3 days |

Two of these deserve explanation:

- **`dbegin` is NetworkOnly.** `createStreamStore`'s poll requests `/spa/network?…&dbegin=<now>` — a unique URL every tick. Cached, they'd churn the entire offline archive out of the LRU within an hour. The same URLs are excluded from the fetch fallback for the same reason.
- **The navigation route exists** because without it a cold start while offline (reopened tab, PWA launch) gets no HTML at all, leaving the precached assets unreachable. The shell names content-hashed assets, so a refresh whenever online keeps it pointing at what the precache currently holds.

Both `/spa/` responses and navigations set `matchOptions: { ignoreVary: true }`. Every `/spa/` response carries `Vary: Accept-Encoding`, and the browser hides `Accept-Encoding` from the service worker's view of a `Request`, so a stored entry can become unmatchable — a cache that looks empty offline.

## 2. Fetch fallback

`installOfflineFallback()` runs in `src/index.tsx` before anything can issue a request. It wraps `window.fetch`: eligible responses are recorded, and a **thrown** fetch — no network reached at all — is answered from the recording.

```
GET + pathname starts with /spa/ + no ?dbegin= → eligible
HTTP errors (401, 500, …) pass through untouched
Bodies over 512 KB are not stored
```

The narrow trigger matters: only a total network failure falls back, so a real server error still looks like a real error rather than silently serving yesterday's data.

This is a single guard beneath all ~54 raw `fetch('/spa/…')` call sites plus `apiFetch`, which is why settings, profiles, widgets and every other endpoint degrade gracefully without per-call-site work. `isCacheableGet` is exported and covered by `offline-fallback.test.ts`:

```bash
node --experimental-strip-types packages/spa-core/src/lib/offline-fallback.test.ts
```

`hasOfflineCopy(url)` reports whether a URL already has a stored copy.

## 3. Message store

`message-store.ts` is a mailbox rather than a response cache — messages accumulate, folders are indexes into them, and the UI reads from disk whether or not there's a network. Three IndexedDB databases (idb-keyval gives one object store per database):

```
hz-inbox-entries   b64mid     -> MessageEntry   list headers, one per message
hz-inbox-lists     listKey    -> b64mid[]       ordered index per feed/folder
hz-inbox-posts     uuid | mid -> raw item       full bodies, for reading offline
```

`listKey` is `` `${type}|${file}` `` — `"|"`, `"direct|"`, `"starred|"`, `"filed|Recipes"`.

### Read-through fetching

`fetchMessages()` replaces what used to live inside `MessageList.tsx`, so HQ's message cards, the folder modal and the inbox all share one mailbox. Online it fetches and records; offline it answers from the store.

Only the first unfiltered page of a list is cacheable. A search or a paged request has nothing stored to fall back on, so offline those return `{ entries: [], offset: -1 }` — an end-of-list reads better than a retry button that cannot work.

### Retention

| What | Rule |
|---|---|
| Starred and filed list indexes | never trimmed — these are what the user deliberately kept |
| Every other list index | most recent 500 |
| Entries | deleted only when no list points at them (`pruneInbox`) |
| Post bodies | ~1000 keys, oldest write first (`prunePosts`); two keys per post |

### Two filling strategies

**The inbox builds everything up front.** Opening `/inbox` runs `syncInbox()`: every feed and folder index, then `warmAllLists()` fetches up to 200 missing post bodies, pinned lists first. That is minutes of background requests on a large mailbox, so it is confined to the module the user actually opened:

- `setInboxActive(true/false)` is set by `InboxView`'s mount/cleanup. `runWarm` re-checks it every iteration, so navigating away stops an in-flight pass mid-list.
- `syncInbox()` is throttled to once per 5 minutes — moving between inbox sections remounts the view and must not re-walk everything. The refresh button passes `force`.
- Warm passes are chained on a promise rather than dropped when one is already running, so the per-list pass and the full sync don't starve each other.

**HQ and the streams accumulate incrementally**, never importing anything up front:

- `fetchNetworkStream` and the channel fetcher call `savePosts(activities)`. Stream responses already carry complete post bodies, so every post scrolled past becomes openable offline **at zero extra request cost**.
- `fetchDisplayItem(id)` records what it fetches, so opening a post is itself what saves it.
- List headers are saved on every `fetchMessages`, everywhere in the app — one write, and it is what keeps HQ's widgets readable offline. Only *body* warming is gated behind `inboxActive`.

### Reading a post offline

`fetchDisplayItem` (`item-api.ts`) is the shared entry point for `PostDetailModal` and `PostView`: it fetches `/spa/display/:id`, and on failure falls back to `getStoredPost(id)`. Posts are indexed by both `uuid` and `mid` because streams open by uuid and permalinks by mid.

Comments are a second request and are **never** pre-fetched. Both views catch a failed comment fetch and render the root alone — a message without its replies beats an error page.

## What is not covered

- **Search** is server-side; offline the box returns nothing.
- **Paging** past a stored window ends the list rather than erroring.
- **Writing** — no outbox. Composing, liking or filing offline fails as it always did.
- **A URL must be fetched once while online** to be readable offline. The inbox sync is the only thing that fetches ahead.

## Debugging

| Symptom | Where to look |
|---|---|
| Nothing works offline at all | Is the SW installed? A failed precache install leaves no worker |
| A list is empty offline | `hz-inbox-lists` for the `type\|file` key |
| A post won't open offline | `hz-inbox-posts` for its uuid/mid |
| Everything else 404s offline | `keyval-store` for `offline:<url>` keys |
| Storage grew unexpectedly | Check for `?dbegin=` keys — those should never be stored |
